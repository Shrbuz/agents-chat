# 会话使用与跨项目接入

本指南随 agent-chat 技能一起安装，适用于已安装该技能的 Codex、Qoder
会话。用户用自然语言指派角色和任务，agent 负责调用 helper 收发消息、
领取任务、发送结果和跟踪验收，不要求用户手写消息 JSON 或执行 Python。

## 已接入项目：为各会话指定角色

角色以当前项目 project.json 的 roles 为准，不要求所有项目都有四角色。
运行 helper 的 `onboard` 可取得本项目每个角色的职责、目录和可复制开场白。
下面四段仅适用于采用默认 Web 四角色的项目，其他角色使用 onboard 的
实际输出。新项目先按 [onboarding.md](onboarding.md) 分析与确认分工。

先打开目标项目目录。各角色必须访问同一份消息存储；同一项目的 linked
worktree 默认共用主 checkout 下该项目的 bus，保留子项目相对路径。
不同机器或独立 clone 需要
配置共享 bus_root，不能仅凭相同项目名判断已经互通。

前端会话：

```text
使用 agent-chat，你负责 frontend。读取项目 AGENTS.md，生成并保留本会话独立 session ID，检查收件箱和未完成任务，然后继续前端工作。需要其他角色协助时按协议发送请求并跟踪回执。
```

后端会话：

```text
使用 agent-chat，你负责 backend。读取项目 AGENTS.md，生成并保留本会话独立 session ID，检查收件箱和未完成任务，然后继续后端工作。处理其他角色的请求后按协议回报结果。
```

运维会话：

```text
使用 agent-chat，你负责 ops。读取项目 AGENTS.md，初始化本会话并检查收件箱。按已有授权处理运维任务，部署完成后向 tester 交接实际版本、地址和验收条件，并跟踪验收结果。
```

测试会话：

```text
使用 agent-chat，你负责 tester。读取项目 AGENTS.md，初始化本会话并检查收件箱。收到部署版本和验收条件后，使用 ego-browser 实操生产站点，记录证据，将问题反馈给对应角色，并跟踪修复后复测。
```

这里的“初始化本会话”表示绑定角色、生成 session ID 和检查任务，已配置
项目不需要重复创建或覆盖。一个会话沿用自己的 session ID；独立新会话
生成新 ID，先恢复未关闭任务，不能直接沿用另一会话的领取令牌。

上述开场白用于首次接入。已经绑定项目和角色的会话，后续直接说任务和
下一步即可，不必每次重复“使用 agent-chat，项目绝对路径”，也不必重复
自己的角色和 session ID。切换项目、首次接入或上下文不明确时再补充。

已有聊天需要显式读取新增/更新的入口。新聊天通过项目 AGENTS.md 接入，
用户仍需明确当前角色。若 Qoder 没显示技能，重新加载技能列表或重启后
确认安装入口。`/agent-ops` 仅在项目确实安装了同名 Qoder command 时可用；
通用技能安装不保证所有项目都有这个快捷命令，上述自然语言用法可复用。

## 日常交互

普通需求直接告诉当前角色。需要跨角色配合时，例如：

```text
这个功能需要后端配合，请把具体需求和验收条件通过 agent-chat 发给后端，并跟踪处理结果。
```

检查进展：

```text
检查收件箱和我发出的未关闭任务，处理可执行事项，汇报需要我决定的问题。
```

恢复空闲的角色会话：

```text
检查收件箱并继续处理，核对自己发出的请求是否已有结果。
```

发出请求的 agent 保留 task_id，接收方 claim 后发送接收回执，完成后
result 回到请求方，由请求方核实并 verify。生产问题由 tester 发给对应
角色，等待修复部署后再按新版本复测。用户无需在这些会话之间复制需求
正文；有关版本、权限或业务取舍的缺失信息仍需明确提供。

## 需要交接时

阶段/任务完成时必须明确交接结论：有新交接、仍待已有任务，或本轮无
新增通知/指令。不因无新增指令就宣称整个项目完成，也不静默省略结论。
工具可用、目标已确认且用户已授权时，agent 必须实际直发，不再让用户
手动转述。成功后说明实际投递结果；不能直发时仍写收件箱并提供可复制
指令。具体规则见 [handoff.md](handoff.md) 和
[原生通知与兼容降级](notifications.md)。

希望启用直发时，在需要发送通知的角色会话中说一次：

```text
启用 agent-chat 的自动交接通知。先检查当前客户端是否有向其他聊天发送消息的工具，并列出本项目相关角色的候选聊天供我确认。等我确认目标并授权后，后续在授权范围内先记录任务，再实际调用工具向目标聊天发送必要的交接通知，不要只给我转发文案。工具不支持时保留共享目录通信并给出可复制指令。
```

确认后沿用本会话的目标与授权范围，不必每次重复指定项目；多会话
同角色时由用户选择实际目标。仅修改/安装本技能不会自动向已有聊天
群发，也不会替其他角色会话获得发送授权。目标可见性、权限和工具以
当前客户端为准：Codex 桌面端的工具不是 Qoder 或其他 agent 的前提。

## 新项目：先初始化一次

在新项目会话中说：

```text
使用 agent-chat 为当前项目规划协作。先分析项目性质，建议最小角色分工、各自职责及需要单独创建或复用的会话。经我确认后，只为选定角色创建通信目录、项目配置和启动入口，并给出各角色可复制的开场指令。保留已有规则，不沿用其他项目的地址、版本或会话绑定。
```

执行此请求的 agent 应：

1. 确认目标项目根目录，读取已有 AGENTS.md、需求/主要项目文件和通信
   配置。按 [onboarding.md](onboarding.md) 建议角色并确认。已初始化时
   保留配置，只补缺失的接入说明，不自动重组角色。
2. 使用已安装技能目录的 `scripts/agent_chat.py`，指定项目绝对路径和
   唯一 project_id。不要要求新项目先拥有 `tools/agent-chat`。

   ```text
   python /absolute/installed/agent-chat/scripts/agent_chat.py --project /absolute/new-project init --project-id unique-project-id --roles builder reviewer
   ```

3. 将生成的 `agent_chat/STARTUP.md` 中启动规则合并到已有 AGENTS.md；
   该文件原本不存在时，init 会创建基础入口。避免覆盖原规则或重复追加。
4. 在该项目 project.json 填实际生产 URL、验收资料和角色默认值。未知
   地址、release_id、账号或部署状态保留未确认状态；不从其他项目复制。
5. 按 [commands.md](commands.md) 检查共享配置，运行 doctor、paths 和
   onboard。建议复用/创建相应角色会话并给出开场白，明确尚未接入的
   角色。只有用户明确要求创建新聊天时才使用平台创建工具。

通用技能内容不存某个项目的会话身份或待办状态。项目事实和消息记录在
各自项目中；运行时消息、证据和本机配置由生成的忽略规则排除出 Git。

## 持续检查与后台唤醒

会话启动、阶段完成、交接和最终回复前检查 inbox/status 已包含在技能
规则中。一个空闲聊天不会仅因收到文件消息自动开始工作。未配置后台
runner 时，需要相应角色继续运行，或用户发出“检查收件箱并继续”。

用户要求无人值守时，在明确角色与 session 的具体会话中配置平台支持
的调度入口。配置方法、持久提示和停止条件见
[scheduling.md](scheduling.md)。watch 只是最长 300 秒的文件等待，不能
作为后台唤醒已经启动的证据。

## 技能位置与维护

整个技能目录需包含 SKILL.md、references 和 scripts。各客户端可安装
同一份目录；本机安装脚本通过 junction 指向技能源，因此更新一份即可
供两个客户端读取。安装位置和 helper 命令见 [commands.md](commands.md)。

如果该安装入口链接到某个仓库，跨项目复用仍依赖这个源目录存在。移动
或删除源仓库前，先把技能迁到长期目录并重新接入两个客户端；不要把
仓库内的项目地址当成所有项目的固定路径。
