# 新项目：分析角色、引导会话、创建通信目录

当用户为新项目启用 agent-chat 时，先根据项目目标、已有文件/需求、交付物、
实际运行环境和协作工具，建议最小可行的角色分工。不把本技能最初的 Web
四角色当成所有项目的组织结构。纯咨询只给建议，不创建目录或聊天。

## 角色建议与确认

说明每个建议角色的职责、产出/验收依据、主要协作对象和是否适合独立
会话。以下是判断示例，不是必须安装的预设：

| 项目性质 | 可建议的最小角色 | 按实际情况再拆分 |
| --- | --- | --- |
| 全栈线上产品 | frontend、backend、ops、tester | 需求复杂时再加 product；小项目可用 builder 合并开发 |
| API 或服务 | backend、reviewer | 需要发布时加 ops，需要独立验收时再拆测试 |
| 脚本、CLI、库 | builder、reviewer | 不因没有网页而强加 frontend 或浏览器 tester |
| 数据分析 | analyst、reviewer | 采集复杂时加 researcher 或 data_engineer |
| 内容与研究 | writer、editor | 有事实调研依赖时加 researcher |
| 视觉/交互交付 | designer、implementer、reviewer | 没有代码交付时不强加开发/运维角色 |

项目类型不明确时只问影响分工的关键信息。一个角色一项清楚的责任边界，
避免每个小步骤都拆会话。已有合适的角色聊天应优先复用。用户确认建议
或明确授权自行规划后才落盘；已有明确角色列表时直接使用，不反复确认。
不要把当前配置咨询会话擅自绑定成交付负责人。

## 初始化与会话开场指令

1. 使用 [commands.md](commands.md) 的 `init --roles` 或 `--roles-file`。
   为确认的角色生成 `<role>_msg` 目录，roles 是唯一的有效路由名单，
   role_descriptions 记录职责。未指定 roles 的 CLI 仍保留四角色默认值，
   只是兼容旧用法，不表示角色分析可以省略。
2. 运行 doctor、paths、onboard，说明真实共享位置。onboard 返回每个
   已配置角色的职责、通信目录和带实际项目路径的启动指令；不创建任务、
   平台聊天或后台服务。将简短入口合并到原 AGENTS.md，保留原项目规则。
3. 向用户建议为确认的角色分别开独立会话，给出每个会话可直接复制的
   开场指令。首次开场包含项目、角色、职责、独立 session、收件箱检查
   和结果/交接规则。优先选现有聊天，不为已绑定会话重复初始化身份。
4. 清楚区分“目录已创建”和“角色聊天已创建/已接入”。只有用户明确
   请求创建具体角色的新聊天，才调用当前平台实际可用的创建工具，并
   遵循其项目选择/目标约束；本指南本身不是创建授权。平台不支持时由
   用户手动开聊天并粘贴指令，不阻塞文件总线使用。不得为跨产品协作
   擅自在 Codex 新建一个本应由 Qoder 承担的角色。
5. 希望直发通知时，按 [notifications.md](notifications.md) 确认实际目标
   聊天及用户授权。创建聊天不等于获得以后互发消息、部署或生产操作的
   权限。没有调度或直发工具时，说明接收方何时检查文件收件箱。

初始化完成的总结要列出：已配置角色与目录、建议创建/复用哪些会话、
哪些尚未接入、用户下一步的实际开场指令。没有其他接入事项时也明确
“本轮无新增交接指令”；不要只说初始化完成。

## 已有项目与角色调整

保持现有角色、目录和历史消息。`init` 不改写既有角色配置，显式传入
不同角色列表会拒绝，避免把历史参与者和未完任务从查询中移除。

追加/重命名/移除已有项目角色不是静默初始化的一部分。先盘点历史和
在途任务、全部客户端/linked worktree 配置及运行中会话，再提出迁移
步骤。只有用户确认迁移后才执行，并同步路由配置、职责、目录和忽略
规则；不能只改一份 project.json 或删除旧目录。当前没有在线角色迁移
命令，保留历史，不能宣称 init 会自动完成这种迁移。
